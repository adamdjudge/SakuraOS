SakuraOS Microkernel Notes
==========================

Boot Process:
- Bootloader loads kernel as well as startup services as modules
- Modules are loaded into sequential physical memory after kernel
- Bootloader passes module parameters array to kernel:
  - Process name
  - Physical base address
  - Virtual address and size of each segment
  - Execution start address
- Configurable module list to change services available on boot
- Kernel and modules are all individual ELF executables
- Kernel creates process and maps segments for each startup service

Message Passing:
- Fully synchronous: sender pauses until target receives message
- Only two syscalls: Call and ReplyRecvAny
- Target/source pid in eax, other arguments in ebx, ecx, edx, esi, edi
- For more data, protocols can define a register as a pointer
- Call:
  - int 0x40
  - Atomically sends message to target pid and waits for reply from same pid
  - Target pid in eax, same on return
- ReplyRecvAny:
  - int 0x41
  - Atomically sends message to target pid and waits for next message from any pid
  - Target pid in eax, on return eax is source pid of next received message
  - Intended for servers to be based on doing this in a loop
- Servers can set their pid to service IDs defined by convention (like TCP ports)
- pid 0 is the kernel, and is used to Call kernel functions (syscalls)
- pids 1 - 0x3fffffff are assigned to new processes on creation
- pids 0x40000000 - 0x7ffeffff can be defined as service IDs
- pids 0x7fff0000 - 0x7fffffff reserved for kernel event messages
- No negative pids: syscalls can return negative error codes in eax

Kernel Events:
- Messages generated by the kernel with source pid in 0x7fff0000 - 0x7fffffff
- Interrupt Events:
  - Processes can register as the handler for interrupts
  - Only one process can be the handler for any interrupt at a time
- Process Events:
  - Things like process death and CPU exceptions
  - Each TCB has a table of pids set to handle these events
  - Message sent to handler contains pid, eip, and possibly other relevant info
  - Handled exceptions pause the offending process until handler replies with status (ok or kill)
  - Kernel has a default behavior for events if no handler is set (usually kill)
  - Default page fault action:
    - Kill process if it accesses kernel memory (below 1G, also catches null deref)
    - Kill process if it writes to a read-only page
    - Otherwise allocate a new blank page (i.e. bss or stack)
    - Just enough for startup services, including the real memory manager
